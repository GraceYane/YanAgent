## 1. 项目目标与对照基线

### 1.1 最终目标

在 YanAgent 中逐步实现一个完整的 Agent Harness（Agent 运行框架），最终在本文列出的功能范围内达到 CowAgentByYan 的使用效果。

用户可以在桌面端、Web 或消息渠道发起任务。系统能够恢复上下文、选择 Agent 与模型、循环调用工具、返回流式进度、保存消息与产物，并支持任务取消、长期记忆、Skills、MCP 和多 Agent 协作。

“达到相同效果”指用户场景和验收行为对齐，允许 YanAgent 使用自己的模块划分和实现方式。各阶段通过验收后逐步扩展，单模型聊天只是第一个交付阶段。

## 3. 最终运行流程与模块边界

```text
桌面 / Web / 消息渠道
         ↓
消息标准化、身份验证、请求校验
         ↓
AgentBridge：路由、运行实例、会话锁、事件队列、取消
         ↓
AgentLoop：组装上下文 → 调用模型 → 判断工具调用
                                ↓
                 权限检查 → ToolManager 执行工具
                                ↓
                 保存 Assistant 工具调用及 Tool Result
                                ↓
                         再次调用模型
                                ↓
                        最终答案与产物
         ↓
事件适配 → SSE / 渠道回复 → 用户界面
```

| 模块 | 负责的事情 | 主要边界 |
|---|---|---|
| 数据契约 | 消息、调用、结果、事件、状态和错误 | 不绑定某个厂商的响应格式 |
| ModelProvider | 请求模型并统一文本、工具调用和用量 | 不调度工具、不操作 HTTP 响应 |
| SessionStore | 持久化消息、运行记录、产物索引及查询 | 数据库存储与模型输入上下文分别管理 |
| ToolManager | 工具注册、Schema、参数、权限和执行 | 内置工具和 MCP 工具使用同一执行入口 |
| AgentLoop | 执行一次模型与工具循环 | 输出内部事件，不直接拼接 SSE |
| AgentBridge | 身份路由、并发、任务生命周期、事件订阅 | 通过 Store 保存数据，不另建一套持久化逻辑 |
| Prompt / Context | 提示词组装、Token 预算、裁剪和摘要 | 不修改完整历史记录来实现上下文裁剪 |
| Memory / Knowledge | 跨会话记忆和用户知识文档 | 与 Session 历史分开，检索结果带来源 |
| Skills / MCP | 流程指令扩展和外部工具接入 | Skill 脚本和 MCP 工具执行仍受工具权限管理 |
| 渠道 / Web API | 输入输出转换和用户交互 | 复用同一个 Runtime |

第一阶段允许增加最小任务管理器以支持流式聊天，后续演进为 AgentBridge。由于当前 HTTP 服务使用线程、核心接口使用异步调用，P01-05 必须确定长期运行的异步执行环境与线程间通信方式，避免每个接口随意创建互不相通的事件循环。

## 5. P01：单模型聊天链路

### 目标

桌面端选择一个已配置模型，发送问题，逐步看到真实回复，能够停止生成并识别调用错误。本阶段先使用当前请求的输入完成回答，多轮历史在 P02 接入。

### 分步骤

- [ ] **P01-01 统一数据契约**：完善 `Message`、`ToolCall`、`ToolResult`、`ModelReply`、`RunRequest` 和 `RunResult`；支持 Assistant 携带工具调用列表；预留用户、Agent、Session、Run 身份；提供 JSON 序列化与必要字段校验。
- [ ] **P01-02 配置与统一错误**：建立配置读取、环境变量覆盖、字段校验和密钥脱敏；保存 Provider、API Base、模型、超时等配置；定义配置、认证、限流、超时和服务端错误。环境变量的优先级高于配置文件。
- [ ] **P01-03 非流式 Provider**：实现一个 OpenAI-compatible Provider；统一消息转换、普通响应、Tool Call 解析、结束原因和 Usage；建立可控制响应序列的 Fake Provider。
- [ ] **P01-04 普通聊天联调**：接通配置与模型查询/保存接口；`/message` 调用 Provider，先用 `inline_reply` 显示完整回答；校验请求并返回明确错误。
- [ ] **P01-05 流式链路**：确定异步执行环境；定义内部事件；实现 Provider 流式响应、文本与工具参数增量组装；创建 `request_id`、事件队列和 SSE 订阅；实现基本取消及任务清理。
- [ ] **P01-06 验证与文档**：覆盖配置、调用、流式错误、停止生成与两次请求隔离；记录真实桌面联调结果；更新阶段状态和开发记录。

### 主要文件

已有：`yanagent/contracts.py`、`yanagent/models/provider.py`、`app.py`。  
建议新增：`yanagent/config/`、`yanagent/errors.py`、`yanagent/events.py`、具体 Provider、Fake Provider 和对应测试。

### 验收标准

1. 从桌面端发出“你好”，能显示真实模型响应；非流式和流式均可验证。
2. 缺少密钥、错误密钥、无效模型、超时、限流和空响应都有可识别反馈，日志不泄露密钥。
3. 停止生成后 UI 结束等待，后台请求被取消或在有限超时内释放，不继续写入已取消 Run。
4. 同时存在两个请求时，事件不会进入错误的请求或会话。
5. Fake Provider 测试离线运行；真实 API 验证单独记录使用的模型和结果。

## 6. P02：Session 与持久化

### 目标

用户可以连续多轮对话，关闭应用后重新启动仍能查看历史并继续交流。

### 分步骤

- [ ] **P02-01 数据库基础**：确定 YanAgent 独立数据目录；使用 SQLite；建立 `sessions`、`messages`、`runs`、`schema_migrations`；从第一版记录 Schema 版本。
- [ ] **P02-02 会话与消息存储**：创建、分页、重命名、置顶、删除会话；事务追加消息；按稳定序号读取；保存时间、归属和元数据。
- [ ] **P02-03 历史与上下文接通**：区分完整历史和本次模型输入；将先前完整轮次传入 Provider；预留工具调用及结果的序列化存储。
- [ ] **P02-04 桌面联调**：接通会话列表、历史、用户消息索引、重命名、删除等界面所需接口；明确单条消息删除、重新生成与后续上下文的处理规则。
- [ ] **P02-05 隔离与恢复**：查询强制校验 `user_id + agent_id + session_id` 归属；处理并发写入；启动时将上次未结束的 Run 标记为中断。

### 验收标准

1. 首轮说明姓名，第二轮询问姓名时可以利用当前 Session 历史回答。
2. 重启后保留消息、顺序、会话名称与置顶状态；另一个会话不会自动获得这些上下文。
3. 错误归属的查询被拒绝；通过绕过 UI 直接访问接口也不能读取其他范围的数据。
4. 部分消息写入失败时事务回滚；迁移前后已有数据可读。
5. 完整历史不会因后续裁剪模型上下文而被物理删除。

## 7. P03：最小工具系统与权限基础

### 目标

工具可以通过统一入口注册、发现、校验和执行，为 Agent Loop 提供稳定依赖。

### 分步骤

- [ ] **P03-01 注册与 Schema**：完善 `ToolDefinition`；支持唯一名称、描述、参数、风险、是否允许并行与作用范围；导出统一 Schema。
- [ ] **P03-02 安全示例工具**：实现 `current_time` 与计算器；计算器使用受限解析，不执行任意代码。
- [ ] **P03-03 参数与结果**：校验必填、类型和未知字段；处理损坏 JSON 和未知工具；统一 `ToolResult`、超时、异常与输出截断。
- [ ] **P03-04 权限基础**：定义 `deny / ask / allow` 的确切语义；限制工具可用范围；为确认流程定义请求 ID 和批准/拒绝结果；尚未接入确认 UI 时，需确认的操作默认拒绝。
- [ ] **P03-05 测试与接口**：接通工具列表；覆盖重复注册、非法参数、权限拒绝、超时和执行失败。

### 验收标准

1. 调用计算器得到正确数值，结果关联原 `tool_call_id`。
2. 参数错误或权限拒绝时 handler 不执行。
3. 执行失败成为结构化 ToolResult，进程继续服务。
4. 大结果被截断且保留截断标记；若结果落盘，文件路径也受工作区权限约束。

## 8. P04：Agent 执行循环

### 目标

用户提出任务后，模型主动选择工具，读取执行结果并继续推理，直到输出最终回答。

### 分步骤

- [ ] **P04-01 Prompt 与上下文组装**：加入身份、系统规则、工具使用说明、历史和当前输入；内部消息格式保持统一。
- [ ] **P04-02 非流式循环**：先用 Fake Provider 完成 `模型 → 工具 → 模型`；保存 Assistant 原始工具调用消息，再保存对应 Tool Result；有工具请求时继续循环。
- [ ] **P04-03 多调用与限制**：先顺序执行同一响应中的多个调用；加入最大轮数、总超时、单工具超时及连续失败限制；明确达到限制后的终态。
- [ ] **P04-04 流式循环**：接入模型增量事件和工具开始/结束事件；工具参数完整解析后才执行；完成事件包含最终答案及累计用量。
- [ ] **P04-05 桌面与持久化联调**：桌面显示文本和工具卡片，历史可还原执行过程，退出后不出现无法解释的半条工具记录。

### 验收标准

1. Fake Provider 连续两轮请求工具、第三轮返回答案，验证调用顺序和每次模型输入。
2. 每次 Tool Result 之前都有相同调用 ID 的 Assistant 工具请求；不能只保存结果而遗漏请求。
3. 实际模型能完成“查询当前时间并说明结果”等工具任务；工具失败后能根据错误继续处理。
4. 未知工具、空内容、空工具调用、参数错误、连续失败及达到轮数上限均能有限结束。
5. 不执行工具的普通问题也能正常结束；每次 Run 只产生一个终态。

## 9. P05：Bridge、上下文与运行稳定性

### 目标

形成可长期使用的单 Agent Runtime：有正确的状态归属、并发控制、取消机制和上下文预算。

### 分步骤

- [ ] **P05-01 Bridge 收口**：将 P01 临时任务管理统一到 `AgentBridge`；管理任务、配置快照、实例缓存、队列、订阅和资源释放。
- [ ] **P05-02 身份与并发**：使用完整身份范围作为路由和锁键；同一 Session 默认排队串行；不同 Session 并发；明确取消排队任务和运行任务的差异。
- [ ] **P05-03 任务控制**：协作式取消、工具取消传播、运行中追加指令；追加消息仅在安全检查点注入，持久化顺序明确；确认 UI 接入批准/拒绝流程。
- [ ] **P05-04 上下文预算**：统计 System Prompt、消息、工具 Schema、记忆和预留输出；截断工具结果；保留完整轮次；历史摘要、手动清空、自动压缩和使用率查询。
- [ ] **P05-05 故障处理**：空响应策略、限流重试与退避、重复调用保护、连接断开处理；已执行的写工具不因模型重试自动重复执行。
- [ ] **P05-06 恢复与观测**：Run 和工具执行状态持久化；记录错误、耗时和 Token；崩溃后识别已完成步骤及不确定副作用，提供显式继续或重试入口。

### 验收标准

1. 两个 Session 并发不串消息；同一 Session 的顺序可预测且不会死锁。
2. 取消只影响目标 Run，工具和事件流在规定超时内终止或被标记为无法立即终止。
3. 长对话在预留输出预算内运行；摘要失败时可降级裁剪；工具请求和结果始终成对保留。
4. 运行中追加的要求在下一个安全检查点生效，重启后仍能查到记录。
5. 崩溃恢复可识别中断及已有步骤；不承诺对外部写操作自动“恰好执行一次”。需要幂等键、结果核对或用户确认的操作有明确处理。

**P01～P05 全部验收后，才认定“单 Agent 核心主链路”完成。**

## 10. P06：多模型、工作区和完整工具能力

### 目标

扩展到参考项目的模型与常用执行能力，让 Agent 能处理实际文件、命令、网页和产物。

### 分步骤

- [ ] **P06-01 多模型与备用链**：Provider 工厂、能力声明、模型目录、会话覆盖配置和备用链；逐项接入参考项目目标模型，包含 DeepSeek、GPT、Qwen、Claude、Gemini 的对应接口。
- [ ] **P06-02 响应差异统一**：处理厂商 Tool Calling、流式、Thinking 字段、结束原因、用量和上下文窗口差异；按供应商公开字段控制显示，防止原始字段意外进入答案或日志。
- [ ] **P06-03 Workspace**：选择和创建工作区、会话项目关联、文件树、读取与编辑；规范路径解析、越界检查及符号链接策略。
- [ ] **P06-04 文件与命令工具**：读取、写入、编辑、列目录、搜索；Bash/命令执行、环境适配、前后台进程、超时、取消及编码处理；接入确认和操作记录。
- [ ] **P06-05 网页与多模态**：搜索、网页提取、浏览器会话、下载；文本/图片/文件内容块；图片理解；语音和其他参考模型能力按对照清单接入。
- [ ] **P06-06 产物与并行**：产物索引、发送、下载和预览；只对允许并行且无依赖的工具并发执行；文件写入冲突可检测。

### 验收标准

1. 每个支持的 Provider 有独立契约测试；有凭据的供应商完成真实测试，未测项明确标注。
2. 主模型失败后可切换备用模型；输出已推送或已有工具副作用时有去重和部分结果策略。
3. Agent 能读取授权工作区的文件、生成新文件并在 UI 展示可打开的产物。
4. 越界路径、未授权命令和未批准写入被拒绝；中文日志和文件内容保持正确编码。
5. 浏览器、网络和命令工具的进程或连接能清理，取消后无持续失控执行。

## 11. P07：Skills 系统

### 目标

用户能安装、管理和使用流程化能力，Agent 根据任务发现并加载相关指令。

### 分步骤

- [ ] **P07-01 本地发现**：扫描 `SKILL.md`、解析 Frontmatter、校验名称和描述；明确内置、用户及工作区的覆盖优先级。
- [ ] **P07-02 Prompt 接入**：先展示元数据，再按需加载完整内容和参考资源；记录本次使用的 Skill 与版本。
- [ ] **P07-03 生命周期**：启用、禁用、创建、编辑、安装、卸载、版本和依赖配置；热刷新后对后续 Run 生效。
- [ ] **P07-04 安装校验**：处理压缩包路径穿越、链接越界、依赖缺失与名称冲突；脚本通过授权工具执行。
- [ ] **P07-05 页面联调**：能力页显示真实列表，读写和管理动作反馈真实结果。

### 验收标准

指定任务能触发对应 Skill 并按约定生成输出；禁用或卸载后不再注入；工作区覆盖规则稳定；运行中的任务保留所用版本信息；无关 Skill 不挤占全部上下文预算。

## 13. P09：长期记忆与知识库

### 目标

Agent 能跨会话记住值得保留的信息，并能检索用户导入的文档。两类数据均具备来源、修改、删除和归属控制。

### 分步骤

- [ ] **P09-01 文本存储**：每日记忆、核心记忆、人工编辑、来源会话/消息、创建及更新时间；先提供关键词检索。
- [ ] **P09-02 自动沉淀**：会话摘要、候选记忆提取、去重、冲突和过时信息更新；避免每句话都保存成长期记忆。
- [ ] **P09-03 向量管线**：结构化切块、Embedding 接口、向量存储、增量索引、重建与模型变更后的兼容处理。
- [ ] **P09-04 检索与注入**：关键词/向量混合召回、Rerank、阈值、来源和 Token 上限；接入记忆搜索/读取工具。
- [ ] **P09-05 知识库**：文档上传、格式提取、分类、索引、检索、引用、删除与重新索引；知识页及参考项目已有展示能力逐项对齐。
- [ ] **P09-06 隔离与质量**：按用户/Agent/共享授权范围检索；删除原文时清理索引与缓存；建立有标注的检索测试集。

### 验收标准

新会话能召回明确保存的偏好并说明来源；修改后的信息优先于过期记录；不同 Agent 的私有记忆不可互读；删除文档后不再从索引召回；知识回答带真实引用；检索未命中时不伪造引用。

## 14. P10：Multi-Agent / Sub-agent

### 目标

用户能创建不同角色的 Agent，主 Agent 可以委派任务并汇总结果，团队会话能明确区分发言者和数据归属。

### 分步骤

- [ ] **P10-01 Agent 配置**：创建、更新、启停、归档/删除；独立身份、模型、Prompt、工具、Skills、知识与工作区配置。
- [ ] **P10-02 单层委派**：父子 Run 关联、任务说明、受限上下文、返回结果、超时、取消和进度事件。
- [ ] **P10-03 并行子任务**：有界并发、结果归属、重复任务检测、失败汇总和委派深度限制。
- [ ] **P10-04 Team 会话**：`@Agent` 解析、会话所属 Agent 与本轮发言 Agent 区分、共享对话可见范围及成员权限。
- [ ] **P10-05 协作展示**：团队管理、子任务工具卡片、成员发言与运行记录；明确共享 Workspace 的写入冲突策略。

### 验收标准

主 Agent 可委派两个子任务并汇总；每个子任务可追踪到父 Run；取消可向下传播；达到最大深度后停止委派；独立 Agent 看不到未授权记忆、文件和私有 Session；团队共享对话按策略可见。

## 15. P11：Web、多渠道、定时与产品管理

### 目标

补齐参考项目的常用管理与接入场景，所有入口复用已实现的 Runtime。

### 分步骤

- [ ] **P11-01 Web 入口与认证**：提供真正可访问的 Web 界面；会话/Token、来源校验、CORS 和文件访问策略；区分本地桌面授权与远程登录。
- [ ] **P11-02 管理接口对齐**：逐页核对团队、模型、知识、记忆、能力、渠道、定时、日志、工作区和产物；补齐真实 CRUD、空状态、错误状态与加载反馈。
- [ ] **P11-03 渠道抽象**：统一文本、图片、语音、文件；用户身份映射、群聊/私聊、去重、回调、流式展示或整条回复和原路返回。
- [ ] **P11-04 渠道逐个接入**：先用 Fake 渠道验证，再接飞书；继续按参考仓库实际清单接入微信/企业微信、钉钉、QQ、Telegram、Slack、Discord 等。每个渠道单独验收和记录凭据/平台限制。

### 验收标准

同一任务从桌面、Web 和已接渠道都可执行并返回正确位置；重复回调不创建重复 Run；授权后才能读取私有数据和产物；定时任务重启后仍存在；运行账本记录实际状态。

需要外部平台凭据的项目，缺少凭据时可记录模拟测试通过与真实验证待完成，不能据此标记为全部对齐。

## 17. 跨阶段接口、数据和质量约定

### 17.1 HTTP 与桌面兼容

以当前 `desktop/src/renderer/src/api/client.ts`、`types.ts` 和 `store/chatStore.ts` 为客户端契约参考。每阶段新增接口时核对实际请求、返回字段和错误处理。

| 接口组 | 首次接入阶段 | 用途 |
|---|---|---|
| `/api/health` | 已有骨架，P01完善 | 存活、就绪、实际能力状态 |
| 配置与模型接口 | P01 | 读取/保存配置、模型与能力列表 |
| `POST /message` | P01 | 接收任务、返回内联回答或 Run 标识 |
| `GET /stream` | P01 | 订阅指定 Run 的 SSE 事件 |
| `POST /cancel` | P01基础、P05完善 | 取消指定请求，校验归属 |
| Session / History | P02 | 会话管理、历史、分页和用户消息索引 |
| Tool / Run / Context | P03～P05 | 工具、运行状态、确认和上下文操作 |
| Workspace / Artifact | P06 | 文件、项目、预览和产物 |
| Skills / MCP / Memory / Knowledge / Agents | P07～P10 | 高级功能管理 |
| Channels / Scheduler / Auth / Logs | P11 | 产品化入口与管理 |

内部事件可使用 `text_delta`、`tool_started` 等名称；输出到现有客户端时转换成其支持的 `delta`、`tool_start`、`tool_end`、`done`、`error` 等事件。所有事件关联 Run 和 Session，保留稳定事件序号。具体字段以联调时的客户端定义为准。

SSE 只断开订阅是否取消任务必须明确区分：普通页面切换不误取消，显式停止才发取消请求。为已结束和过期 Run 定义查询结果、队列保留时长及重连策略。

### 17.2 数据与运行状态

- 使用独立 YanAgent 数据目录，不读写 CowAgent 原有配置、密钥和数据库。
- 数据库建立版本迁移，从初始化版本开始测试；后续新增表按阶段迁移。
- 建议 Run 状态：`queued → running → completed / failed / cancelled / interrupted`，终态不可被迟到事件改写。
- 工具确认可使用独立等待状态或事件，必须有超时；进程重启不能默认恢复已批准的危险操作。
- 完整历史、模型上下文、长期记忆与知识库分别管理。
- 用量缺失标记为未知，估算与供应商实际返回分开记录。
- 任务恢复先实现可诊断中断和显式继续；自动恢复仅在有检查点和副作用策略的范围内启用。

### 17.3 测试与完成定义

每个业务需求的完成条件：

1. 实际功能实现，目标路径不再使用固定成功响应或空列表冒充可用功能。
2. 核心逻辑有可重复的行为测试，包含失败路径；不为简单文案变更增加无意义测试。
3. 涉及接口时进行接口测试；涉及桌面页面时进行对应页面联调和前端构建。
4. 使用 Fake Model/Tool/Clock/Transport，离线测试不依赖真实密钥或公网。
5. 网络、第三方平台和安装包分别做实际环境验证，未验证项目如实记录。
6. 更新本文任务状态和 `workProcess.md`，附验证命令或证据位置。

常用检查以实际依赖和框架为准。当前 Python 入口：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m compileall -q app.py yanagent
```

桌面变更后在 `desktop` 目录执行：

```powershell
npm run build
```

### 17.4 每阶段应明确的运行限制

模型调用、工具执行、队列长度、并发数、事件保留、上下文预算及产物大小都有可配置上限。取消和错误最终必须释放资源。执行文件/命令/网络工具时同步实现对应权限和访问范围，不能推迟到最终打包阶段。

响应性能和成功率目标在得到可重复基线后制定，并固定测试任务、模型版本和环境，避免将不同条件下的结果直接比较。

## 19. 后续推进与记录方式

1. 本文是后续阶段顺序、范围和验收的主要依据；`IMPLEMENTATION_ROADMAP.md` 作为导航摘要。
2. 每次需求使用编号，例如“开发 P01-01”；先读取现有实现和该任务依赖，再开始修改。
3. 开始时将阶段标记为“进行中”；子任务验收通过才勾选；阶段所有必需项通过后标记“已完成”。
4. 每次需求在 `workProcess.md` 末尾记录：日期、任务编号、需求、实际改动、文件、验证结果和剩余事项。
5. 文档和开发记录反映已发生的工作；已设计不等于已实现，已实现不等于已真实联调。
6. 新发现的参考功能、接口冲突或环境限制，先写明对范围和顺序的影响，再更新文档版本。

### 第一次开发任务

**P01-01：完善统一消息数据结构。**

交付物为数据契约、中文字段说明、JSON 序列化/还原和必要校验测试。使用下面的固定消息序列验收：

```text
User：计算 1 + 2
Assistant：tool_calls = [{id: call_001, name: calculator, arguments: ...}]
Tool：tool_call_id = call_001，content = 3
Assistant：计算结果是 3
```

四条消息能完整保存和还原，工具调用与结果不会丢失对应关系。通过后进入 P01-02。
